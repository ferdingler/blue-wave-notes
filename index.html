What Is An OS Boundary?

The operating system is a privileged resource manager. A sandbox is a narrower contract for what the kernel or trusted brokers will do for a process.

Learning Objectives

  • Explain user space vs kernel space.
  • Identify resources the OS mediates.
  • Separate isolation from high-level policy.
  • Understand what an escape means.

Core Idea

Applications do not touch disks, sockets, process tables, devices, or other processes directly. They ask the kernel. The sandbox reduces what the kernel or a trusted broker will do on behalf of the process.

Why It Exists

Without a privileged mediator, one program could overwrite another program's memory, read arbitrary storage, configure hardware, bind any port, or impersonate any user. OS boundaries let mutually suspicious programs share one machine.

Linux Mechanics

Linux uses CPU privilege levels, virtual memory, process credentials, file permissions, capabilities, namespaces, cgroups, Linux Security Modules such as SELinux/AppArmor/Landlock, and seccomp filters. Processes enter the kernel through syscalls, faults, interrupts, and signals.

macOS and Windows

macOS uses XNU, POSIX permissions, Seatbelt/App Sandbox, entitlements, SIP, TCC privacy controls, XPC, and code signing. Windows uses NT objects, access tokens, SIDs, ACLs, integrity levels, AppContainer, Job Objects, capabilities, and Hyper-V-backed isolation.

Can Enforce

  • Access to kernel-mediated resources.
  • Filesystem, process, network, IPC, and device visibility.
  • Resource limits and privilege reductions.

Cannot Enforce

  • Application correctness.
  • Secrets already loaded into memory.
  • Kernel bugs or hardware attacks.
  • Behavior outside the mediated path.

Optional Lab

On Linux, run:

uname -a
id
ulimit -a
mount | head
ps aux | head

For each output, label the OS resource or policy surface it describes.

Gotcha: Containers are OS isolation, not VM isolation. They share the host kernel unless backed by a VM or microVM.

Processes

A process is an execution container: address space, threads, credentials, environment, open descriptors, current directory, limits, and kernel bookkeeping.

Learning Objectives

  • Define process, thread, PID, parent, and child.
  • Understand inheritance across process creation.
  • Explain why file descriptors and environment matter.

Core Idea

A sandbox normally starts by launching untrusted code as a separate process, then reducing what that process inherits and what it can ask the OS to do.

Why It Exists

Processes let many programs share hardware while preserving private memory and controlled access to shared resources. Threads share a process address space; processes do not.

Linux Mechanics

Linux creates tasks with fork(), clone(), and execve(). fork() copies process state using copy-on-write. execve() replaces the program image but preserves selected state, including PID, credentials, environment, working directory, resource limits, and file descriptors not marked close-on-exec.

macOS and Windows

macOS is Unix-like and supports fork()/exec(), though post-fork behavior in multi-threaded programs is delicate. Windows primarily uses CreateProcess, explicit handle inheritance, access tokens, environment blocks, and Job Objects; it has no normal fork() equivalent.

Can Enforce

  • Memory isolation between processes.
  • Lifecycle control and process tree supervision.
  • Descriptor, environment, and credential hygiene at launch.

Cannot Enforce

  • Least privilege by itself.
  • Safe use of inherited secrets.
  • Termination of all descendants unless process groups, jobs, or subreapers are used.

Optional Lab

echo $$
ps -o pid,ppid,pgid,sid,comm -p $$
ls -l /proc/$$/fd
env | sort | head

Start a child shell and compare PID, PPID, file descriptors, environment, and working directory.

Gotcha: File descriptors are capabilities. A child with an open descriptor to a secret can keep using it even if the path later disappears from its filesystem view.

Users, Groups, and Permissions

Identity gives the kernel a subject to authorize. It is necessary for sandboxing, but not sufficient.

Learning Objectives

  • Understand UID/GID, real/effective IDs, and groups.
  • Explain permission bits, ACLs, and capabilities.
  • Know why same-UID sandboxes are weak.

Core Idea

The OS asks: who is making this request? Then it checks object permissions, capabilities, policy modules, and namespace state.

Linux Mechanics

Linux processes have real, effective, saved, and filesystem UIDs/GIDs plus supplementary groups. Files have owner, group, mode bits, and optionally ACLs. Root traditionally bypasses many checks, but Linux capabilities split root power into units such as CAP_NET_ADMIN, CAP_SYS_ADMIN, CAP_SYS_PTRACE, and CAP_SYS_CHROOT.

macOS and Windows

macOS has POSIX users/groups, ACLs, entitlements, TCC, SIP, and sandbox profiles. Windows centers on access tokens containing SIDs, groups, privileges, integrity level, and capabilities; objects have security descriptors and ACLs.

Can Enforce

  • File ownership boundaries.
  • Service account separation.
  • Reduced privileged operations through capability dropping.

Cannot Enforce

  • Network egress by itself.
  • Fine-grained application intent.
  • Access through already-open descriptors.
  • Security if broad capabilities remain.

Optional Lab

id
touch /tmp/perm-demo
ls -l /tmp/perm-demo
chmod 600 /tmp/perm-demo
ls -l /tmp/perm-demo

If available, try sudo -u nobody cat /tmp/perm-demo and observe the denial.

Gotcha: CAP_SYS_ADMIN is famously broad. In many sandbox designs, retaining it is close to retaining root-shaped escape power.

Syscalls

Syscalls are the kernel API. Every file, process, network, memory, and device operation eventually crosses this boundary.

Learning Objectives

  • Define a syscall.
  • Recognize major syscall families.
  • Use strace to observe process behavior.
  • Understand why syscall filtering is low-level.

Core Idea

User code cannot open a file, connect a socket, map memory, or start a process directly. It asks the kernel through a syscall such as openat, connect, mmap, clone, or execve.

Linux Mechanics

libc usually wraps raw syscalls, but programs can invoke them directly. The kernel dispatches by syscall number, copies arguments across the user/kernel boundary, validates pointers and permissions, updates state, then returns a value or errno.

macOS and Windows

macOS has BSD syscalls plus Mach traps and higher-level security mechanisms. Windows applications usually call Win32 APIs above lower-level NT syscalls; syscall numbers are not a stable application contract.

Can Enforce

  • Deny process creation, networking, tracing, module loading, mount operations, or dangerous syscall families.
  • Reduce kernel attack surface.

Cannot Enforce

  • High-level intent.
  • Safe path decisions without additional context.
  • Meaning of pointer-referenced data in general.

Optional Lab

strace -f -e trace=file,process,network ls /tmp

Notice how much work happens before the visible command output appears: dynamic linking, locale, filesystem probes, and process setup.

Gotcha: write() might write a harmless log or exfiltrate a secret. Syscall filters see mechanism, not business intent.

Filesystem Isolation

Filesystem isolation changes which names exist and what storage those names point to.

Learning Objectives

  • Distinguish permissions from namespace isolation.
  • Understand chroot, pivot_root, bind mounts, mount namespaces, tmpfs, and overlayfs.
  • Recognize symlink and open-FD hazards.

Core Idea

A path such as /etc/passwd is resolved through root directory, current directory, mount table, credentials, and permissions. Change the mount table and root, and the process sees a different world.

Linux Mechanics

Linux mount namespaces give a process tree its own mount table. Sandboxes combine bind mounts, read-only remounts, private mount propagation, tmpfs, overlayfs, pivot_root or chroot, and a carefully curated /proc, /dev, and /sys.

macOS and Windows

macOS uses App Sandbox file entitlements, TCC privacy prompts, SIP, POSIX permissions, ACLs, and sandbox profiles; Linux-style mount namespaces normally require a Linux VM. Windows uses ACLs, AppContainer capabilities, integrity levels, Windows containers, and object namespaces.

Can Enforce

  • Hide or replace path hierarchies.
  • Expose selected paths read-only.
  • Provide disposable writable layers.

Cannot Enforce

  • Network or CPU limits.
  • Safety if mount privileges remain.
  • Protection from already-open file descriptors.
  • Kernel filesystem bugs.

Optional Lab

sudo unshare --mount bash
mount --make-rprivate /
mkdir -p /tmp/sandbox-root/tmp
mount -t tmpfs tmpfs /tmp/sandbox-root/tmp
mount | grep sandbox-root

This demonstrates a private mount change. Do not run broad mount commands on a production host.

Gotcha: chroot alone is not a strong sandbox, especially for privileged processes. Treat it as one filesystem-shaping tool, not a complete boundary.

Process Isolation

Process isolation controls which processes can see, signal, debug, wait for, or inherit from each other.

Learning Objectives

  • Understand PID namespaces, /proc, signals, process groups, and sessions.
  • Know why PID 1 is special.
  • Understand ptrace and process inspection risks.

Core Idea

Untrusted code should not be able to inspect or interfere with host processes. A sandbox also needs lifecycle control over all descendants.

Linux Mechanics

PID namespaces give processes a separate PID view. The first process becomes PID 1 inside that namespace and must reap orphaned children. Process visibility also depends on /proc mounts, credentials, capabilities, ptrace restrictions, sessions, process groups, cgroups, and Yama settings.

macOS and Windows

macOS lacks Linux-style PID namespaces and relies on users, sandbox profiles, SIP, hardened runtime, launchd, and XPC. Windows uses access tokens, integrity levels, Job Objects, AppContainer, process mitigation policies, and container silos.

Can Enforce

  • Hide host PIDs.
  • Prevent ordinary signaling and debugging across boundaries.
  • Manage a sandbox process tree.

Cannot Enforce

  • CPU or memory limits without resource controls.
  • Filesystem or network restrictions.
  • Child cleanup unless PID 1 or a supervisor does the work.

Optional Lab

sudo unshare --pid --fork --mount-proc bash
ps aux
echo $$

The shell should appear as PID 1 inside the new namespace.

Gotcha: A PID namespace without a private /proc produces confusing and sometimes leaky visibility.

Network Isolation

Network isolation changes interfaces, routes, ports, firewall state, DNS behavior, and which remote systems a process can reach.

Process
socket(), connect()
→
Network namespace
interfaces, routes, loopback
→
Firewall / NAT / Proxy
egress control
→
Remote endpoint
internet, metadata, internal service

Learning Objectives

  • Understand sockets, loopback, routes, NAT, veth pairs, and firewalls.
  • Explain proxy-only egress.
  • Know why HTTP_PROXY is not a boundary.

Core Idea

Network access is a combination of socket syscalls, namespace state, routing tables, packet filters, DNS configuration, and reachable local/remote services.

Linux Mechanics

Linux network namespaces isolate interfaces, routing tables, ARP tables, port binding space, and packet-filter state. Containers commonly connect through a veth pair and bridge, then use NAT or routed networking. A fresh namespace starts with loopback down.

macOS and Windows

macOS does not provide Linux network namespaces for ordinary processes; Docker Desktop uses a VM. macOS controls include PF, Network Extension, entitlements, and application firewall. Windows uses Windows Filtering Platform, firewall rules, HNS/WinNAT, AppContainer network capabilities, and Hyper-V isolation.

Can Enforce

  • No network by omitting interfaces/routes.
  • Separate loopback and port spaces.
  • Egress through firewall or proxy.
  • Metadata service blocking.

Cannot Enforce

  • Application-layer policy by itself.
  • DNS safety unless resolver path is controlled.
  • Strong egress if privileged code can reconfigure networking.

Optional Lab

sudo unshare --net bash
ip link
ping -c 1 127.0.0.1
ip link set lo up
ping -c 1 127.0.0.1

Observe that even loopback must be explicitly enabled in a fresh namespace.

Gotcha: HTTP_PROXY is configuration. A generated binary can ignore it unless direct egress is blocked at the network layer.

Seccomp

Seccomp restricts which syscalls a process may make. It reduces kernel attack surface; it does not understand business intent.

Learning Objectives

  • Understand seccomp strict vs BPF filter mode.
  • Know allowlist vs denylist tradeoffs.
  • Understand KILL, ERRNO, TRAP, TRACE, LOG, and USER_NOTIF style outcomes.

Core Idea

Even after filesystem and network isolation, a compromised process can exercise a large kernel API. Seccomp blocks syscalls the workload should never need.

Linux Mechanics

Seccomp filter mode uses BPF programs installed by the process or runtime. Filters match syscall number and limited argument values, then return an action such as allow, kill, return errno, trap, trace, log, or user notification. Filters are inherited across fork() and execve().

macOS and Windows

macOS does not have seccomp; similar goals are covered by Seatbelt/App Sandbox, entitlements, SIP, hardened runtime, and Endpoint Security. Windows uses AppContainer, restricted tokens, process mitigation policies, Win32k lockdown, object ACLs, and WDAC/AppLocker.

Can Enforce

  • Block syscall classes.
  • Reduce kernel attack surface.
  • Make dangerous operations fail even if app code is compromised.

Cannot Enforce

  • High-level meaning of a request.
  • Path policy reliably.
  • Inspection of pointer data in general.
  • Safety after overly broad syscalls are allowed.

Optional Lab

docker run --rm alpine sh -c 'grep Seccomp /proc/self/status'
docker run --rm --security-opt seccomp=unconfined alpine sh -c 'grep Seccomp /proc/self/status'

Compare the seccomp mode under Docker's default profile and unconfined mode.

Gotcha: Denylists age poorly as new syscalls appear. For strong workloads, prefer allowlists shaped from observed behavior and tested under realistic startup paths.

Cgroups and Resource Isolation

A process can be safely denied sensitive resources and still harm the host by consuming all CPU, memory, PIDs, disk, or IO.

Learning Objectives

  • Understand CPU, memory, PID, IO, and device controls.
  • Know cgroup v1 vs v2 exists.
  • Compare Linux cgroups to Windows Job Objects.

Core Idea

Resource isolation makes abuse survivable. It is the practical defense against fork bombs, memory bombs, and noisy-neighbor failures.

Linux Mechanics

Cgroups group processes into a hierarchy with controllers. In cgroup v2, common files include cpu.max, memory.max, pids.max, io.max, and pressure stall information. systemd, Docker, Kubernetes, and container runtimes build on cgroups.

macOS and Windows

macOS has setrlimit, launchd limits, QoS classes, and memory pressure systems but no direct cgroup equivalent. Windows has Job Objects, working-set limits, CPU rate controls, memory limits, quotas, and container resource governance.

Can Enforce

  • CPU quotas and weights.
  • Memory ceilings and OOM behavior.
  • Maximum process counts.
  • Some block IO throttling.

Cannot Enforce

  • Perfect latency guarantees.
  • All disk capacity limits without quotas.
  • Network bandwidth without traffic controls.
  • Application-level fairness.

Optional Lab

systemd-run --user --scope -p MemoryMax=200M -p CPUQuota=50% bash
cat /proc/self/cgroup

This starts a scoped shell with systemd-managed resource controls, where available.

Gotcha: Memory limits often end in an OOM kill, not a clean exception. Application runtimes may need their own heap settings aligned with the cgroup limit.

Containers, VMs, and microVMs

Containers restrict a process's view of one host kernel. VMs run a separate guest kernel. microVMs try to make VM isolation operationally lightweight.

Learning Objectives

  • Distinguish containers, VMs, and microVMs.
  • Know which Linux primitives make containers work.
  • Decide when sharing a kernel is acceptable.

Core Idea

Containers are packaged process isolation. VMs are kernel isolation. microVMs are optimized VMs intended to reduce the cost of stronger isolation.

First Principles

A program is isolated only to the extent that its view of files, processes, network, users, devices, clocks, kernel APIs, and hardware is controlled. Containers are namespaced processes. VMs virtualize hardware and boot a guest OS. microVMs use minimal VMMs such as Firecracker or Cloud Hypervisor for fast, high-density VM isolation.

Linux Mechanics

Containers combine namespaces, cgroups, capabilities, seccomp, pivot_root, bind mounts, overlay filesystems, and LSMs. VMs usually use KVM plus QEMU or another VMM. microVMs use KVM with minimal devices, often virtio.

Platform Notes

Docker on macOS usually runs Linux containers inside a Linux VM. Windows has Windows containers, Hyper-V isolation, Job Objects, AppContainers, integrity levels, and Windows Sandbox. Linux containers and Windows containers are different OS-specific mechanisms.

Can Enforce

  • Namespace and cgroup separation.
  • Kernel attack surface reduction.
  • Stronger kernel separation with VM/microVM.

Cannot Enforce

  • Protection from shared-kernel bugs in plain containers.
  • Safety from privileged containers.
  • Secret isolation if secrets are mounted or inherited.

Optional Lab

docker run --rm -it --network=none --pids-limit=64 --memory=128m --cap-drop=ALL alpine sh

Inside, inspect /proc, try networking, and compare visibility with the host.

Gotcha: Mounting /var/run/docker.sock into a container usually grants near-host-root control.

Shells and Command Execution

A shell is an interpreter that turns text into process creation, pipes, redirects, expansion, and file descriptor manipulation.

Learning Objectives

  • Understand shell parsing, expansion, redirection, and pipelines.
  • Know why argument arrays are safer than shell strings.
  • Understand command injection and PATH risks.

Core Idea

The OS executes an executable path with argv, environment, cwd, descriptors, and credentials. A shell adds a language on top of that. That language is powerful and easy to misuse.

Linux and macOS

A shell typically forks, creates pipes with pipe(), redirects descriptors with open() and dup2(), then calls execve(). It expands variables, globs, quotes, command substitutions, redirects, conditionals, and pipelines before the target program runs.

Windows

Windows process creation centers on CreateProcess and a command-line string. cmd.exe, PowerShell, MSVCRT, and custom parsers differ. There is no single universal Unix-style argv parsing rule.

Can Help Enforce

  • Semantic command policy if the shell is controlled.
  • Safer execution through fixed paths and argv arrays.
  • Environment and cwd control.

Cannot Enforce

  • Safety when untrusted input is concatenated into shell strings.
  • Isolation from native binaries that bypass the shell.
  • Protection from inherited FDs or credentials.

Optional Lab

Compare a shell string and an argument array in your preferred language. Test inputs such as hello; id, $(id), and *.txt.

Gotcha: Escaping is harder than avoiding the shell. Prefer argv APIs unless you explicitly need shell language features.

Video search: command injectionOWASP: command injection

Interpreters and Generated Code

The kernel sees syscalls from a process. It does not care whether the process is running compiled code, Python, Node, templates, or generated source.

Learning Objectives

  • Recognize interpreter boundaries.
  • Separate data parsing from code execution.
  • Understand why generated native code still needs OS controls.

Core Idea

Interpreter hooks can add semantic policy, but the OS boundary must still mediate the effects of code the interpreter does not understand.

First Principles

An interpreter takes input and executes behavior described by that input. Sometimes the input is obviously code. Sometimes it is configuration, templates, regexes, SQL, YAML tags, serialized objects, workflow definitions, or generated source.

Linux Mechanics

Interpreter-specific controls live above the kernel: restricted language subsets, process separation, OS namespaces, seccomp, cgroups, read-only filesystems, or VM/microVM boundaries. Shebang scripts use #! so the kernel invokes an interpreter path with the script as input.

Platform Notes

macOS is similar for Unix runtimes. Windows uses file associations, PATHEXT, explicit launchers, PowerShell execution policy, application control, .NET/JVM runtime mechanisms, and browser engine sandboxes.

Can Enforce

  • Domain-specific constraints with deliberately limited languages.
  • Safer plugins through process isolation.
  • Policy when runtime hooks are complete.

Cannot Enforce

  • Security if filesystem/network/native APIs remain exposed.
  • Resource safety without CPU/memory/time limits.
  • Safety from injection into generated source.

Optional Lab

Render user input through a template engine and test engine-specific syntax such as {{ 7 * 7 }}. Confirm whether the engine treats it as text or executable template logic.

Gotcha: "Safe eval" is rarely safe unless the language was designed for confinement and the runtime API surface is deliberately small.

File Descriptors and IPC

File descriptors are references to kernel objects. In practice, they are capabilities.

Learning Objectives

  • Understand FDs, pipes, sockets, shared memory, and Unix domain sockets.
  • Know how FDs survive fork and exec.
  • Recognize descriptor leaks as authority leaks.

Core Idea

If a process has a descriptor, it may use the object even if path-based permissions would no longer let it open that object.

Linux Mechanics

open() returns a descriptor. read(), write(), ioctl(), poll(), epoll(), sendmsg(), and recvmsg() operate on descriptors. fork() inherits descriptors. execve() preserves them unless FD_CLOEXEC is set. Unix domain sockets can pass FDs with SCM_RIGHTS.

macOS and Windows

macOS has POSIX descriptors, Unix sockets, kqueue, Mach ports, and XPC. Windows uses handles for files, processes, threads, tokens, events, pipes, sections, sockets, and more; inheritance and duplication use CreateProcess, DuplicateHandle, ACLs, and Job Objects.

Can Enforce

  • Narrow access by passing only specific descriptors.
  • Brokered designs with privileged holders.
  • Path-independent pre-opened resource access.

Cannot Enforce

  • Safety if powerful descriptors leak.
  • Path restrictions after directory FDs are inherited.
  • Protocol correctness over IPC.

Optional Lab

ls -l /proc/$$/fd
exec 3</etc/passwd
ls -l /proc/$$/fd

Notice the new descriptor. If passed to a child, it carries read authority.

Gotcha: A host directory FD plus openat() can bypass naive path assumptions.

Credentials and Secret Boundaries

A secret is any value that grants access if copied. A sandbox that exposes secrets has already granted authority.

Learning Objectives

  • Separate identity, authorization, credentials, and secret material.
  • Find common secret exposure paths.
  • Understand brokered credential use.

Core Idea

If untrusted code receives a raw bearer secret, policy has already lost meaningful control over how that authority is used.

Where Secrets Appear

Credentials can live in environment variables, config files, mounted volumes, process memory, crash dumps, swap, logs, /proc, local agents, Unix sockets, cloud metadata services, browser stores, keychains, and credential helpers.

Linux Mechanics

Linux controls include file permissions, namespaces, hidepid on /proc, prctl dumpability, tmpfs, keyrings, capabilities, mlock, and LSM policies. Kernel credentials such as UID/GID/capabilities are different from application credentials such as API keys and AWS tokens.

macOS and Windows

macOS commonly uses Keychain, app sandbox entitlements, TCC, SIP, and launchd. Windows uses Credential Manager, DPAPI, protected LSASS material, access tokens, ACLs, integrity levels, AppContainers, and service accounts.

Can Enforce

  • Scoped, short-lived credential use.
  • Secret retrieval outside untrusted code.
  • Audit through identity-aware helpers.

Cannot Enforce

  • Protection after a raw secret is handed to malicious code.
  • Safety from logs and crash dumps unless controlled.
  • Least privilege if all workloads share a credential.

Optional Lab

env | sort
tr '\0' '\n' < /proc/$$/environ

Identify variables you would not want inherited by an untrusted child process.

Gotcha: Environment variables are convenient, inherited by default, easy to dump, and frequently logged.

User-Space Gateways and Proxies

A gateway is a trusted broker. The sandbox asks the broker for a narrow operation instead of receiving direct access to the resource.

Learning Objectives

  • Explain brokered access.
  • Distinguish advisory proxies from enforced egress paths.
  • Identify gateway bypass and confused-deputy risks.

Core Idea

A gateway is useful only if the sandbox makes it the effective path to the resource. Otherwise it is just a convention.

Sandboxed process
No raw secret, no direct route
→
Gateway
authenticate, authorize, validate, log
→
Credential provider
sign or inject if allowed
→
Remote API
AWS, MCP, OpenAPI, model provider

Linux Mechanics

Gateways use Unix sockets, network proxies, local endpoints, FUSE, D-Bus, sidecars, or seccomp user notification. The key condition is that direct access is blocked; otherwise the process can route around the broker.

macOS and Windows

macOS uses XPC, launchd services, Network Extension, app sandbox brokers, and permission prompts. Windows uses services, named pipes, RPC, COM brokers, AppContainer brokers, Windows Filtering Platform, and enterprise proxy controls.

Can Enforce

  • Allowlisted operations.
  • Central auth, validation, rate limits, and audit.
  • Credential use without handing raw secrets to the process.

Cannot Enforce

  • Security if clients can bypass the gateway.
  • Safety from confused-deputy broker bugs.
  • No exfiltration through allowed channels unless content/volume is controlled.

Optional Lab

Run a local mock HTTP service that allows only one path. Configure a test process to use it, then confirm that a direct call fails when network isolation blocks non-proxy egress.

Gotcha: A proxy is not a boundary if direct sockets, SSH, DNS tunneling, metadata endpoints, or privileged Unix sockets remain reachable.

Observability and Debugging

Debugging a sandbox means asking what world the process sees, and what operation the kernel or broker denied.

Learning Objectives

  • Inspect namespaces, mounts, FDs, cgroups, and network state.
  • Trace syscalls and denials.
  • Map application symptoms to enforcing layers.

Core Idea

Most sandbox failures surface as generic errors. Observability lets you identify whether the denial came from filesystem, network, capability, seccomp, cgroup, LSM, or policy.

Linux Inspection Toolkit

# Process state
cat /proc/<pid>/status
cat /proc/<pid>/limits
cat /proc/<pid>/cgroup

# Namespaces and mounts
ls -l /proc/<pid>/ns
lsns -p <pid>
cat /proc/<pid>/mountinfo

# File descriptors and sockets
ls -l /proc/<pid>/fd
lsof -p <pid>

# Capabilities and network
grep Cap /proc/<pid>/status
getpcaps <pid>
nsenter -t <pid> -n ip addr
nsenter -t <pid> -n ss -tulpn

# Syscalls and denials
strace -f -e trace=file,network,process ./program
journalctl -k
ausearch -m SECCOMP,AVC,USER_AVC

macOS and Windows

macOS: ps, lsof, log stream, log show, Instruments, and limited dtruss depending on SIP. Windows: Process Explorer, Process Monitor, Event Viewer, ETW, whoami /priv, icacls, and WFP inspection tools.

Can Help Identify

  • Which namespace and cgroup a process is in.
  • Which files and sockets are open.
  • Which syscall failed and with which errno.
  • Whether a policy layer logged a denial.

Cannot Prove

  • That the sandbox is complete.
  • That all denials are logged.
  • That no side channel exists.
  • That debug access is safe to grant broadly.

EACCESUnix permissions, ACL, read-only mount, LSM, parent directory execute bit.
EPERMMissing capability, seccomp, namespace restriction, immutable flag, LSM.

Optional Lab

sudo unshare --net --fork bash
ip addr
ping -c 1 8.8.8.8

From another terminal, find the PID and inspect /proc/<pid>/ns and nsenter -t <pid> -n ip addr.

Gotcha: Debug access can weaken isolation. Granting SYS_PTRACE or broad /proc access is itself a security decision.

16

Sandboxing Failure Modes

Real sandbox failures are usually composition mistakes, not one primitive completely missing.

Learning Objectives

  • Recognize inherited authority, mount exposure, and network escape paths.
  • Separate isolation failures from policy failures.
  • Design for fail-closed behavior.

Core Idea

A sandbox fails when constrained code can affect something outside the intended boundary. Most failures come from shared resources you forgot were still shared.

Common Failure Categories

CategoryExampleMitigation
Inherited authorityOpen FD to a secret survives exec.Close FDs, use O_CLOEXEC, inspect /proc/<pid>/fd.
Mount exposureWritable host directory mounted in sandbox.Narrow bind mounts, read-only where possible, nodev, nosuid, noexec.
Network escapeMetadata service reachable.Egress firewall, network namespace, metadata proxy or block.
Privileged socketDocker socket mounted inside container.Do not expose host control sockets.
Capability leakCAP_SYS_ADMIN retained.Drop all capabilities; add back only specific ones.
Weak syscall filterDangerous syscalls still allowed.Use tested allowlists where practical.
Process escapeHelper launched outside constraints.Apply sandbox before exec and supervise the process tree.
Resource exhaustionFork bomb or memory spike.cgroups, rlimits, PID limits.

Platform Examples

Linux failures often involve namespace sharing, broad mounts, retained capabilities, missing seccomp, weak cgroups, leaked FDs, and host sockets. macOS failures often involve over-broad entitlements, TCC grants, helper tools outside the sandbox, and XPC confusion. Windows failures often involve token/ACL mistakes, named pipe or COM exposure, Job Object escape, AppContainer capability mistakes, and writable directories in privileged search paths.

Analysis Can Improve

  • Trust-boundary clarity.
  • Least privilege.
  • Fail-closed startup.
  • Escape-relevant tests and monitoring.

Cannot Guarantee

  • Kernel vulnerability resistance.
  • Correctness of all dependencies.
  • Safety if privileged host interfaces are intentionally exposed.
  • Protection from all side channels.

Optional Lab

exec 3</etc/passwd
bash -c 'ls -l /proc/$$/fd'

Observe inherited descriptors. The child has access even if later path restrictions would hide /etc/passwd.

Gotcha: Debug flags, --privileged, host PID/network namespaces, broad writable mounts, and unconfined seccomp profiles can collapse a sandbox while still making it look "containerized".

Putting The Primitives Together

A practical sandbox is a composition. Each layer narrows one dimension of authority.

Learning Objectives

  • Combine filesystem, network, process, syscall, and resource controls.
  • Understand why layering matters.
  • Map a workload contract to OS primitives.

Core Idea

No primitive expresses the whole security policy. A coherent sandbox is a deliberately composed environment with explicit limits and explicit escape assumptions.

Minimal Linux Walkthrough With bubblewrap

bubblewrap exposes Linux sandboxing primitives directly without requiring you to write a runtime. Install it only on a machine where these experiments are appropriate.

# Debian/Ubuntu
sudo apt-get install bubblewrap

mkdir -p /tmp/sandbox-work

bwrap \
  --unshare-all \
  --share-net \
  --die-with-parent \
  --new-session \
  --ro-bind /usr /usr \
  --ro-bind /bin /bin \
  --ro-bind /lib /lib \
  --ro-bind /lib64 /lib64 \
  --ro-bind /etc/ld.so.cache /etc/ld.so.cache \
  --ro-bind /etc/resolv.conf /etc/resolv.conf \
  --proc /proc \
  --dev /dev \
  --tmpfs /tmp \
  --bind /tmp/sandbox-work /work \
  --chdir /work \
  --setenv HOME /work \
  --setenv PATH /usr/bin:/bin \
  /bin/sh

Inside the sandbox, try pwd, touch allowed.txt, ls /, ls /home, ps aux, and ls -l /proc/$$/fd. To remove network access, do not share the network namespace; exact behavior depends on host configuration and privileges.

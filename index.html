Curriculum Map

The course is organized around authority: what a process receives, what the kernel mediates, what a broker mediates, and what must be verified.

Part I
Execution

Goal: Understand what a process is before you try to confine one.

Study OS boundaries, process creation, inheritance, credentials, file descriptors, and syscalls. By the end you should be able to explain exactly what changes across fork(), execve(), descriptor inheritance, environment inheritance, and UID/GID checks.

Part II
Isolation

Goal: Build a smaller world for the workload.

Study filesystem views, mount namespaces, PID namespaces, network namespaces, IPC visibility, cgroups, capabilities, and seccomp. The key question is not "is it in a container?" The key question is "what names, routes, kernel APIs, resources, and privileges exist from inside?"

Part III
Policy

Goal: Know where semantic policy can and cannot live.

Kernel primitives know files, sockets, syscalls, credentials, and resource usage. Gateways and brokers know API methods, model requests, MCP tools, cloud actions, and business policy. Strong sandboxing combines both: low-level primitives force all sensitive actions through a semantic decision point.

Part IV
Verification

Goal: Prove the boundary you think you built is the one the process actually sees.

Use /proc, strace, lsns, nsenter, cgroup files, audit logs, firewall state, gateway logs, and negative tests. A professional sandbox course should teach denials as first-class artifacts, not only successful demos.

Part V
Composition

Goal: Assemble a workload contract into a concrete sandbox.

The capstone at the end asks you to build a no-network workspace sandbox, then evolve it into a gateway-only agent environment with no raw cloud credentials. That is the shape used by real agent sandboxes: isolate the execution world, then broker the intentional powers.

What you should be able to do after the course: Given a proposed sandbox design, inventory inherited authority, identify bypass routes, map each guarantee to a kernel or broker enforcement point, and write tests that fail when the boundary is accidentally weakened.

Sandboxing starts with a contract. The primitives are implementation tools, not the goal.

A useful sandbox contract is concrete: "This workload may read this input tree, write this output tree, run these tools, call this gateway, consume this much CPU and memory, and persist these audit events." Everything else is denied or absent. If the contract is vague, the implementation will become a pile of unrelated restrictions.

What Is An OS Boundary?

The operating system is a privileged resource manager. A sandbox is a narrower contract for what the kernel or trusted brokers will do for a process.

Learning Objectives

  • Explain user space compared with kernel space.
  • Identify resources the OS mediates.
  • Separate isolation from high-level policy.
  • Understand what an escape means.

Core Idea

Applications do not touch disks, sockets, process tables, devices, or other processes directly. They ask the kernel. The sandbox reduces what the kernel or a trusted broker will do on behalf of the process.

Instructor Lecture: The Kernel Is The Referee

A backend service usually feels like it "opens a file" or "calls an API." At the OS level, the process asks the kernel to open a file descriptor, connect a socket, map memory, create a child, or signal another process. The kernel is the component that knows about credentials, file permissions, mount tables, network interfaces, process tables, cgroups, and syscall filters.

A sandbox is not a library that politely asks application code to behave. A sandbox is a modified relationship between a process and the kernel or a trusted broker. If generated code can reach the resource without going through that relationship, the sandbox is advisory.

Checkpoint: If someone says "we block curl in the shell," ask what happens when the agent writes a Go program that calls connect() directly. If the answer depends on shell cooperation, the boundary is not below the workload.

Why It Exists

Without a privileged mediator, one program could overwrite another program's memory, read arbitrary storage, configure hardware, bind any port, or impersonate any user. OS boundaries let mutually suspicious programs share one machine.

Linux Mechanics

Linux uses CPU privilege levels, virtual memory, process credentials, file permissions, capabilities, namespaces, cgroups, Linux Security Modules such as SELinux/AppArmor/Landlock, and seccomp filters. Processes enter the kernel through syscalls, faults, interrupts, and signals.

macOS and Windows

macOS uses XNU, POSIX permissions, Seatbelt/App Sandbox, entitlements, SIP, TCC privacy controls, XPC, and code signing. Windows uses NT objects, access tokens, SIDs, ACLs, integrity levels, AppContainer, Job Objects, capabilities, and Hyper-V-backed isolation.

Can Enforce

  • Access to kernel-mediated resources.
  • Filesystem, process, network, IPC, and device visibility.
  • Resource limits and privilege reductions.

Cannot Enforce

  • Application correctness.
  • Secrets already loaded into memory.
  • Kernel bugs or hardware attacks.
  • Behavior outside the mediated path.

Processes

A process is an execution container: address space, threads, credentials, environment, open descriptors, current directory, limits, and kernel bookkeeping.

Learning Objectives

  • Define process, thread, PID, parent, and child.
  • Understand inheritance across process creation.
  • Explain why file descriptors and environment matter.

Core Idea

A sandbox normally starts by launching untrusted code as a separate process, then reducing what that process inherits and what it can ask the OS to do.

Why It Exists

Processes let many programs share hardware while preserving private memory and controlled access to shared resources. Threads share a process address space; processes do not.

Linux Mechanics

Linux creates tasks with fork(), clone(), and execve(). fork() copies process state using copy-on-write. execve() replaces the program image but preserves selected state, including PID, credentials, environment, working directory, resource limits, and file descriptors not marked close-on-exec.

Instructor Lecture: Process Creation Is Authority Transfer

The moment a supervisor launches a sandboxed workload, it decides what authority crosses the boundary. The executable path, argv, environment, current directory, UID/GID, supplementary groups, resource limits, signal disposition, process group, and file descriptors all matter. execve() changes the program image, but it does not magically remove authority the process already holds.

That is why sandbox launchers are careful about close-on-exec, environment allowlists, current directory, process groups, subreapers, and kill-on-parent-death behavior. A sandbox boundary that starts after the child has inherited host descriptors and secrets is already late.

Users, Groups, and Permissions

Identity gives the kernel a subject to authorize. It is necessary for sandboxing, but not sufficient.

Learning Objectives

  • Understand UID/GID, real/effective IDs, and groups.
  • Explain permission bits, ACLs, and capabilities.
  • Know why same-UID sandboxes are weak.

Core Idea

The OS asks: who is making this request? Then it checks object permissions, capabilities, policy modules, and namespace state.

Linux Mechanics

Linux processes have real, effective, saved, and filesystem UIDs/GIDs plus supplementary groups. Files have owner, group, mode bits, and optionally ACLs. Root traditionally bypasses many checks, but Linux capabilities split root power into units such as CAP_NET_ADMIN, CAP_SYS_ADMIN, CAP_SYS_PTRACE, and CAP_SYS_CHROOT.

Instructor Lecture: Identity Is Necessary But Not Sufficient

Credentials answer "who is asking?" They do not answer the whole sandbox question. A same-UID sandbox can often read the same files and signal the same processes as the parent. A root process with broad capabilities can reshape mounts, configure networking, trace processes, or bypass normal permission checks.

Capabilities split root into named powers, but several are still broad. CAP_SYS_ADMIN is especially dangerous because it covers many operations that affect namespaces, mounts, and kernel state. A strong agent sandbox normally starts by dropping all capabilities and then proves that none are required for the workload class.

User namespaces complicate the word "root." A process can be root inside its namespace while mapping to an unprivileged UID outside. Inspect /proc/<pid>/uid_map and /proc/<pid>/gid_map before assuming what root means.

Syscalls

Syscalls are the kernel API. Every file, process, network, memory, and device operation eventually crosses this boundary.

Learning Objectives

  • Define a syscall.
  • Recognize major syscall families.
  • Use strace to observe process behavior.
  • Understand why syscall filtering is low-level.

Core Idea

User code cannot open a file, connect a socket, map memory, or start a process directly. It asks the kernel through a syscall such as openat, connect, mmap, clone, or execve.

Linux Mechanics

libc usually wraps raw syscalls, but programs can invoke them directly. The kernel dispatches by syscall number, copies arguments across the user/kernel boundary, validates pointers and permissions, updates state, then returns a value or errno.

Instructor Lecture: Syscalls Are The Kernel API

Generated code can use a shell, Python, Node, Go, Rust, C, package-manager hooks, or a native binary. The kernel does not care. It sees syscalls such as openat, connect, mmap, clone, execve, ioctl, and ptrace. That is why low-level confinement must be below language and tool choices.

Syscalls are also too low-level to express most business policy. write() might write a harmless log or exfiltrate a secret. connect() might reach a trusted gateway or an attacker-controlled host. Use syscall filtering for attack-surface reduction, then use higher-level brokers for semantic authorization.

macOS has BSD syscalls plus Mach traps and higher-level security mechanisms. Windows applications usually call Win32 APIs above lower-level NT syscalls; syscall numbers are not a stable application contract.

  • Reduce kernel attack surface.

  • High-level intent.
  • Safe path decisions without additional context.
  • Meaning of pointer-referenced data in general.

Filesystem Isolation

Filesystem isolation changes which names exist and what storage those names point to.

Learning Objectives

  • Distinguish permissions from namespace isolation.
  • Understand chroot, pivot_root, bind mounts, mount namespaces, tmpfs, and overlayfs.
  • Recognize symlink and open-FD hazards.

Core Idea

A path such as /etc/passwd is resolved through root directory, current directory, mount table, credentials, and permissions. Change the mount table and root, and the process sees a different world.

Linux Mechanics

Linux mount namespaces give a process tree its own mount table. Sandboxes combine bind mounts, read-only remounts, private mount propagation, tmpfs, overlayfs, pivot_root or chroot, and a carefully curated /proc, /dev, and /sys.

Instructor Lecture: Namespaces Change What Exists

A mount namespace is a separate map from path names to mounted filesystems. It does not primarily say "no"; it makes parts of the host world absent from the process's point of view. If /home/fdingler/.aws is not mounted, the process cannot read it by accident.

This is powerful but easy to overestimate. A mount namespace does not close file descriptors that were opened before entering the namespace. A directory FD inherited from the host can still be used with openat(). Filesystem isolation is therefore both a launch hygiene problem and a mount design problem.

Path Resolution Anatomy

When a process opens ../../somewhere/file, the kernel resolves that name from a starting point: either the current working directory, root directory, or a directory file descriptor used by APIs such as openat(). During resolution it follows mount points, checks execute/search permission on parent directories, handles symlinks unless told not to, and finally checks object permissions and LSM policy.

ConceptWhy It Matters In A Sandbox
Current directoryA child can inherit a cwd inside a host path even if the visible root changes later. Launchers should set cwd deliberately.

SymlinkA symlink can redirect name lookup. Use mount design and safe open APIs rather than trusting string prefixes.

Design Patterns

  • Workspace-only write: bind the workspace read-write, bind the toolchain read-only, use tmpfs for scratch, and hide the real home directory.
  • Immutable toolchain: expose compilers and runtimes read-only so generated code can run but cannot patch the tools.
  • Disposable overlay: use overlayfs or a temp writable layer when the workload expects a normal root filesystem but changes should be thrown away.
  • No host control sockets: do not mount Docker, containerd, SSH agent, desktop bus, or credential helper sockets unless they are the explicit broker.

Verification Checklist

  1. Inspect /proc/<pid>/mountinfo and confirm every mount is intentional.
  2. Attempt reads from home, parent repo directories, cloud config, SSH config, package manager credentials, and host temp paths.
  3. Attempt writes to system paths, read-only binds, hidden host paths, and scratch paths.
  4. List /proc/<pid>/fd and confirm no host directory or secret FDs survived launch.
  5. Check whether /proc, /sys, and /dev are minimal and tied to the sandbox context.

macOS and Windows

macOS uses App Sandbox file entitlements, TCC privacy prompts, SIP, POSIX permissions, ACLs, and sandbox profiles; Linux-style mount namespaces normally require a Linux VM. Windows uses ACLs, AppContainer capabilities, integrity levels, Windows containers, and object namespaces.

Can Enforce

  • Hide or replace path hierarchies.
  • Expose selected paths read-only.
  • Provide disposable writable layers.

Cannot Enforce

  • Network or CPU limits.
  • Safety if mount privileges remain.
  • Protection from already-open file descriptors.
  • Kernel filesystem bugs.

Process Isolation

Process isolation controls which processes can see, signal, debug, wait for, or inherit from each other.

Learning Objectives

  • Understand PID namespaces, /proc, signals, process groups, and sessions.
  • Know why PID 1 is special.
  • Understand ptrace and process inspection risks.

Core Idea

Untrusted code should not be able to inspect or interfere with host processes. A sandbox also needs lifecycle control over all descendants.

Linux Mechanics

PID namespaces give processes a separate PID view. The first process becomes PID 1 inside that namespace and must reap orphaned children. Process visibility also depends on /proc mounts, credentials, capabilities, ptrace restrictions, sessions, process groups, cgroups, and Yama settings.

Instructor Lecture: PID Visibility Is Not Resource Control

A PID namespace changes which processes exist from the workload's point of view. It helps prevent casual host process discovery, signaling, and debugging. It does not stop a process from spawning too many children, consuming CPU, or exhausting memory. Pair PID namespaces with cgroup pids.max, CPU, and memory limits.

The first process in a PID namespace is PID 1 and has special lifecycle responsibilities. If it does not reap children, zombies accumulate. A sandbox supervisor must think about process groups, sessions, subreapers, and shutdown behavior, not only initial process launch.

macOS and Windows

macOS lacks Linux-style PID namespaces and relies on users, sandbox profiles, SIP, hardened runtime, launchd, and XPC. Windows uses access tokens, integrity levels, Job Objects, AppContainer, process mitigation policies, and container silos.

Can Enforce

  • Hide host PIDs.
  • Prevent ordinary signaling and debugging across boundaries.
  • Manage a sandbox process tree.

Cannot Enforce

  • CPU or memory limits without resource controls.
  • Filesystem or network restrictions.
  • Child cleanup unless PID 1 or a supervisor does the work.

Learning Objectives

  • Understand sockets, loopback, routes, NAT, veth pairs, and firewalls.
  • Explain proxy-only egress.
  • Know why HTTP_PROXY is not a boundary.

Core Idea

Network access is a combination of socket syscalls, namespace state, routing tables, packet filters, DNS configuration, and reachable local/remote services.

Linux Mechanics

Linux network namespaces isolate interfaces, routing tables, ARP tables, port binding space, and packet-filter state. Containers commonly connect through a veth pair and bridge, then use NAT or routed networking. A fresh namespace starts with loopback down.

Instructor Lecture: A Gateway Is Only A Boundary If It Is The Only Door

Environment variables such as HTTP_PROXY are hints to cooperative programs. A compromised process, generated binary, or library that ignores proxy variables can call connect() directly unless the network boundary prevents it. For a gateway to be security-bearing, direct routes must be absent, firewalled, or otherwise impossible for the sandboxed process.

Once the gateway is the only path, it can safely hold credentials outside the workload. The sandbox sends an unsigned request; the gateway parses fields, evaluates policy, signs or injects credentials only if allowed, and logs the result.

Proxy-Only Egress Pattern

A proxy-only design has three parts. First, the sandbox has no direct route to the internet or sensitive internal networks. Second, the only reachable endpoint is the proxy or gateway. Third, the proxy authenticates the workload, evaluates policy, logs the decision, and forwards only allowed requests. Omitting the first step makes the proxy advisory, not enforcing.

Seccomp

Seccomp restricts which syscalls a process may make. It reduces kernel attack surface; it does not understand business intent.

Learning Objectives

  • Compare seccomp strict mode with BPF filter mode.
  • Compare allowlist and denylist tradeoffs.
  • Understand KILL, ERRNO, TRAP, TRACE, LOG, and USER_NOTIF style outcomes.

Core Idea

Even after filesystem and network isolation, a compromised process can exercise a large kernel API. Seccomp blocks syscalls the workload should never need.

Linux Mechanics

Seccomp filter mode uses BPF programs installed by the process or runtime. Filters match syscall number and limited argument values, then return an action such as allow, kill, return errno, trap, trace, log, or user notification. Filters are inherited across fork() and execve().

Instructor Lecture: Seccomp Is A Seatbelt, Not A Steering Wheel

Seccomp can say "this process may never call mount()" or "return EPERM for ptrace()." It cannot reliably say "this write is business-safe" or "this openat() is allowed because the path is inside the repo" without help from other primitives.

The right use of seccomp is attack-surface reduction. If a coding agent only needs normal file IO, process creation, and network through a gateway, it should not need kernel module loading, raw device access, keyring manipulation, arbitrary namespace creation, or debugging other processes.

Profile Design Lifecycle

  1. Observe realistic behavior. Trace cold start, warm path, DNS, subprocesses, dynamic linking, language runtime startup, package-manager hooks, and shutdown.
  2. Classify syscalls by family. File IO, memory, process, network, signals, time, futexes, epoll, namespace, mount, keyring, module, BPF, ptrace, device, and raw socket calls have different risk profiles.
  3. Drop capabilities first. Seccomp is more effective when privileged syscalls would fail anyway due to missing capabilities.
  4. Set no_new_privs. This prevents gaining privilege across exec and is commonly required for unprivileged seccomp installation.
  5. Choose fail behavior deliberately. ERRNO is debuggable, KILL is stricter, LOG is useful during rollout, and USER_NOTIF introduces a broker.
  6. Test negative cases. Attempt mount, ptrace, namespace creation, raw sockets, keyring access, module loading, and BPF operations.

Cgroups and Resource Isolation

A process can be safely denied sensitive resources and still harm the host by consuming all CPU, memory, PIDs, disk, or IO.

Learning Objectives

  • Understand CPU, memory, PID, IO, and device controls.
  • Distinguish cgroup v1 from cgroup v2.
  • Compare Linux cgroups to Windows Job Objects.

Core Idea

Resource isolation makes abuse survivable. It is the practical defense against fork bombs, memory bombs, and noisy-neighbor failures.

Linux Mechanics

Cgroups group processes into a hierarchy with controllers. In cgroup v2, common files include cpu.max, memory.max, pids.max, io.max, and pressure stall information. systemd, Docker, Kubernetes, and container runtimes build on cgroups.

Instructor Lecture: Hiding Is Not Limiting

Namespaces change what a process can see. Cgroups bound what a process tree can consume. A sandbox that hides the host filesystem and network can still hurt the machine by creating too many processes, allocating too much memory, or saturating CPU and IO.

Resource limits should attach to the whole sandbox tree, not only the first child. That is why cgroups are a better fit than process-local limits for aggregate memory, CPU, and PID control.

rlimits Compared With cgroups

rlimit values are per-process or per-user limits inherited at process creation. They are useful for simple ceilings such as file size, open files, or address-space hints. Cgroups apply to a set of processes and descendants, which makes them better for supervising an entire sandbox tree. A robust launcher often uses both: rlimits for process-local guardrails and cgroups for aggregate resource governance.

Production Gotchas

  • Memory limits can kill the process rather than raising a language-level exception. Runtime heap settings should be below the cgroup limit.
  • PID limits must include helper processes, shells, language workers, compilers, tests, and package manager hooks.
  • Disk consumption is not fully solved by memory and CPU cgroups. Use quotas, scratch volumes, cleanup, and log limits.
  • Nested runtimes such as Docker-in-Docker, build tools, and test harnesses may create subprocesses outside the expected scope unless the launcher attaches the whole tree.
  • User delegation depends on systemd and host configuration. Labs that use systemd-run --user may need host setup.

Learning Objectives

  • Understand shell parsing, expansion, redirection, and pipelines.
  • Know why argument arrays are safer than shell strings.
  • Understand command injection and PATH risks.

Core Idea

The OS executes an executable path with argv, environment, cwd, descriptors, and credentials. A shell adds a language on top of that. That language is powerful and easy to misuse.

Linux and macOS

Windows

Can Help Enforce

  • Environment and cwd control.

Cannot Enforce

  • Safety when untrusted input is concatenated into shell strings.
  • Isolation from native binaries that bypass the shell.
  • Protection from inherited FDs or credentials.

File Descriptors and IPC

File descriptors are references to kernel objects. In practice, they are capabilities.

Learning Objectives

  • Understand FDs, pipes, sockets, shared memory, and Unix domain sockets.
  • Know how FDs survive fork and exec.
  • Recognize descriptor leaks as authority leaks.

Core Idea

If a process has a descriptor, it may use the object even if path-based permissions would no longer let it open that object.

Linux Mechanics

open() returns a descriptor. read(), write(), ioctl(), poll(), epoll(), sendmsg(), and recvmsg() operate on descriptors. fork() inherits descriptors. execve() preserves them unless FD_CLOEXEC is set. Unix domain sockets can pass FDs with SCM_RIGHTS.

Instructor Lecture: File Descriptors Are Capabilities

High-level engineers often think in paths: /tmp/foo, /var/run/docker.sock, ~/.aws/credentials. The kernel often thinks in open objects. Once a process has a file descriptor, the path is no longer the only source of authority. The descriptor may continue to work after permissions change, after a file is deleted, or after the process enters a different mount namespace.

Unix domain sockets make this more subtle because descriptors can be sent over IPC with SCM_RIGHTS. A process may receive authority that never appears as a path. Windows has the same concept through inheritable and duplicated handles. Different names, same principle: handles and descriptors are authority.

Checkpoint: A filesystem sandbox is incomplete until you inspect /proc/<pid>/fd or the platform equivalent. The visible path tree is not the whole authority set.

Credentials and Secret Boundaries

A secret is any value that grants access if copied. A sandbox that exposes secrets has already granted authority.

Learning Objectives

  • Separate identity, authorization, credentials, and secret material.
  • Find common secret exposure paths.
  • Understand brokered credential use.

Core Idea

If untrusted code receives a raw bearer secret, policy has already lost meaningful control over how that authority is used.

Where Secrets Appear

Credentials can live in environment variables, config files, mounted volumes, process memory, crash dumps, swap, logs, /proc, local agents, Unix sockets, cloud metadata services, browser stores, keychains, and credential helpers.

Instructor Lecture: Raw Secrets Collapse Policy

A bearer credential grants access to whoever copies it. API keys, session tokens, SSH private keys, cookies, and many cloud credentials are bearer-like in practice. Once untrusted generated code sees them, it can often use them outside the intended workflow until they expire or are revoked.

Brokered authority keeps the raw secret outside the sandbox. The workload asks for an operation. A trusted component validates the request, signs or performs the request if allowed, logs the decision, and returns only the result. This preserves policy leverage because the sandbox never receives a reusable credential.

  • Central auth, validation, rate limits, and audit.
  • Credential use without handing raw secrets to the process.

Cannot Enforce

  • Security if clients can bypass the gateway.
  • Safety from confused-deputy broker bugs.
  • No exfiltration through allowed channels unless content/volume is controlled.

Observability and Debugging

Debugging a sandbox means asking what world the process sees, and what operation the kernel or broker denied.

Learning Objectives

  • Inspect namespaces, mounts, FDs, cgroups, and network state.
  • Trace syscalls and denials.
  • Map application symptoms to enforcing layers.

Core Idea

Most sandbox failures surface as generic errors. Observability lets you identify whether the denial came from filesystem, network, capability, seccomp, cgroup, LSM, or policy.

Sandboxing Failure Modes

Real sandbox failures are usually composition mistakes, not one primitive completely missing.

Learning Objectives

  • Recognize inherited authority, mount exposure, and network escape paths.
  • Separate isolation failures from policy failures.
  • Design for fail-closed behavior.

Core Idea

A sandbox fails when constrained code can affect something outside the intended boundary. Most failures come from shared resources you forgot were still shared.

Common Failure Categories

CategoryExampleMitigation
Inherited authorityOpen FD to a secret survives exec.Close FDs, use O_CLOEXEC, inspect /proc/<pid>/fd.
Mount exposureWritable host directory mounted in sandbox.Narrow bind mounts, read-only where possible, nodev, nosuid, noexec.
Network escapeMetadata service reachable.Egress firewall, network namespace, metadata proxy or block.
Privileged socketDocker socket mounted inside container.Do not expose host control sockets.
Capability leakCAP_SYS_ADMIN retained.Drop all capabilities; add back only specific ones.
Weak syscall filterDangerous syscalls still allowed.Use tested allowlists where practical.
Process escapeHelper launched outside constraints.Apply sandbox before exec and supervise the process tree.
Resource exhaustionFork bomb or memory spike.cgroups, rlimits, PID limits.

Platform Examples

Linux: Check namespace sharing, broad mounts, retained capabilities, missing seccomp, weak cgroups, leaked FDs, and host sockets.

macOS: Check broad entitlements, Transparency, Consent, and Control grants, helper tools outside the sandbox, and XPC authorization.

Windows: Check token and access-control-list mistakes, named pipes, COM brokers, Job Object membership, AppContainer capabilities, and privileged search paths.

Analysis Can Improve

  • Trust-boundary clarity.
  • Least privilege.
  • Fail-closed startup.
  • Escape-relevant tests and monitoring.

Cannot Guarantee

  • Kernel vulnerability resistance.
  • Correctness of all dependencies.
  • Safety if privileged host interfaces are intentionally exposed.
  • Protection from all side channels.

Capstone: Design A Gateway-Only Agent Sandbox

Produce a reviewable sandbox design with a contract, authority inventory, implementation plan, tests, and readiness rubric.

The capstone scenario is a coding-agent workload. It receives a workspace, runs tools, executes generated code, and may call approved services through a gateway. It must not read the host home directory, inherit host credentials, contact the internet directly, inspect host processes, exhaust host resources, or mutate host control surfaces.

Phase 1: Authority Inventory

Before implementing anything, write down every authority the workload might receive.

AuthorityInventory QuestionsTarget Answer
ExecutableWhat binary starts? Who controls it? Can it spawn children?Supervisor starts a known launcher; children remain in the sandbox scope.
IdentityWhich UID/GID/capabilities? Any user namespace mapping?Unprivileged identity; capabilities dropped; UID/GID map documented if used.
FDsWhich descriptors are open at exec?Only stdio and intentional broker descriptors; all others close-on-exec or closed.
EnvironmentWhich variables survive?Allowlisted minimal environment; no cloud, SSH, package, or session secrets.
FilesystemWhich paths are readable and writable?Workspace writable; toolchain read-only; synthetic home; no host control sockets.
NetworkWhich interfaces, routes, DNS, and sockets exist?No direct egress; only gateway socket or explicitly routed proxy path.
ResourcesWhat CPU, memory, PIDs, disk, and time limits apply?Cgroup and timeout limits sized for workload class.
PolicyWhere are decisions made and enforced?Gateway or supervisor is the enforcement point; decisions are logged.

Phase 2: Build The Minimal World

Create a sandbox that can run a shell and simple language runtime with no network. The goal is not maximum functionality; the goal is a known baseline.

  1. Start a child process with a sanitized environment and closed descriptors.
  2. Create private mount, PID, IPC, and network namespaces.
  3. Mount only the toolchain, runtime libraries, minimal /dev, private /proc, synthetic HOME, and writable workspace.
  4. Drop capabilities and set no_new_privs.
  5. Attach cgroup limits for memory, CPU, PIDs, and runtime timeout.
Exit criteria: Inside the sandbox, direct network fails, host home is absent, host PIDs are hidden, system paths are read-only, and only intentional FDs are visible.

Phase 3: Add Gateway-Only Egress

Add exactly one path to external capability: a gateway. The gateway holds credentials, evaluates policy, validates structured request fields, forwards only allowed operations, and logs decisions.

Gateway ConcernDesign Requirement
AuthenticationIdentify the sandbox session and parent user; do not trust self-asserted identity from the workload.
AuthorizationEvaluate action, resource, context, and temporal state before forwarding.
Credential handlingCredentials remain in the gateway or credential service; the sandbox receives no reusable bearer secret.
Protocol validationParse structured fields; reject unknown methods, destinations, and oversized payloads.
AuditLog request ID, principal, workload, action, resource, context hash or safe fields, decision, reason, and result.
Failure modeGateway unavailable means sensitive operations fail closed; the sandbox does not fall back to direct access.

Phase 4: Add Seccomp And LSM Defense In Depth

Once the workload runs, observe its syscall surface and apply a seccomp profile. Use ERRNO or logging during development, then tighten. Use AppArmor, SELinux, or Landlock where available to reinforce filesystem and process restrictions. Do not use seccomp as a substitute for mount/network isolation.

  1. Trace normal startup and representative tasks.
  2. Deny mount, namespace creation, raw sockets, keyring, module loading, BPF/perf, ptrace, io_uring_setup, and dangerous device operations unless explicitly required.
  3. Run negative tests for each denied family.
  4. Document platform-specific gaps and whether the sandbox fails closed.

Phase 5: Verification Suite

Write tests that fail if the sandbox weakens. These are not unit tests for happy-path features; they are boundary regression tests.

TestExpected Result
Read ~/.aws/credentials, ~/.ssh, parent repo, and host temp secret.Denied or path absent.
List host PIDs and signal a host process.Host PIDs absent; signal fails.
Direct curl by hostname and IP.Fails without reaching network.
DNS lookup and DNS-over-HTTPS.Fails or goes only through controlled resolver/gateway.
Reach metadata endpoint.Blocked or narrow proxy response with no raw credentials.
Open Docker socket, SSH agent, desktop bus, or credential helper.Socket absent unless intentionally brokered.

Production Readiness Rubric

Boundary

Every contract statement maps to a kernel or broker enforcement point. No sensitive behavior relies only on cooperation from generated code.

Least Privilege

Capabilities, mounts, env, FDs, routes, and credentials are allowlisted. Broad host surfaces are absent by default.

Fail Closed

Missing namespace support, gateway outage, policy load failure, or cgroup setup failure prevents the workload from starting in a weaker mode.

Observability

Denied operations can be attributed to a layer: filesystem, network, cgroup, seccomp, LSM, or gateway policy.

Regression Tests

Negative tests run in CI or release validation and cover known bypass paths.

Platform Honesty

Linux, macOS, and Windows guarantees are documented separately, with explicit unsupported or best-effort modes.
